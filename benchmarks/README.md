# Reproducible benchmark harness

The harness was added in Phase 2.4a. Phase 2.4b adds two real public OSS
pilot tasks to the catalog; Phase 2.4d prepared three more, which were subsequently executed once each. The five historical records are retained in `results/`. `REPORT.md` is generated by the
report command from structured result records only. It is not a performance
claim. See [Phase 2.4b pilots](#phase-24b-pilots) below.

See also the [comparison protocol](COMPARISON_PROTOCOL.md). Phase 2.4g implements the opt-in direct arm
(see [Direct comparison arm](#direct-comparison-arm-phase-24g)); no comparison has been run.

Real paired direct-comparison token or cost savings are **unproven**. The five historical TaskStance records and `REPORT.md` are preserved unchanged. The report's historical limitation sentence that the harness only runs TaskStance is stale: the current harness also has an opt-in direct arm, with no real paired comparison evidence.

Each task directory contains a strict `manifest.json`, a provider-neutral
`project.json`, and checked-in `*.local.example.json` files that show the
structure of the machine-local configuration. The manifests reference
`.local/codex.json` (and, for Pilot B, `.local/judgment.json`). These live only
on the operator's machine and are ignored by Git (`.local/`), so no launcher
path or other machine-specific value is committed. Result records keep the
SHA-256 of the exact local config bytes as provenance.

### Methodology

- Two small public OSS pilot tasks were selected from historical merged PRs
  (clsx#82, yoctocolors#26). Those PRs were used only to choose the tasks and
  to design behavior checks. The historical patch is not in the task summary,
  manifests, notes, judgment process, adapter configuration or verification.
  The executor sees only the task statement, the declared initial context
  files, and whatever it inspects in the disposable checkout itself.
- Each pilot was executed once in a quota-controlled session limited to one
  executor launch with no retries, and no comparison run was made.
- Both pilots map every TaskStance model tier to the same Codex model
  (`gpt-6.1-sol`). Differences between profiles therefore appear in reasoning
  effort and the other policy dimensions, not in a silent model change.
  Pilot A's deterministic `minimal` reasoning is raised to Codex `low` by the
  existing adapter. Pilot B's fixed-control `medium` is passed through
  unchanged.
- Verification uses only Node.js built-ins. No upstream dependencies are
  installed. Pilot A checks that both benchmark links in `readme.md` are
  repository-relative and that no root-relative link remains. Pilot B sets
  `FORCE_COLOR=1`, imports `./index.js`, and requires one exact nested
  bold/dim output string. Each check prints nothing and exits non-zero on
  mismatch or error. Both checks were confirmed to fail on the pinned
  baselines before any live run.
- The pilot B fixed-control judgment
  ([`tools/fixed-judgment.mjs`](tools/fixed-judgment.mjs)) runs through the
  existing generic `process` judgment adapter. It reads one request, emits one
  constant profile (primary / balanced / medium / small / targeted / targeted /
  direct, `parallel_safe` false, confidence 0.99), and imports no modules. It
  does not read files, use the network, Git or environment variables, or echo
  the task. Provider identity comes from the local configuration.
  **The fixed-control judgment exercises the real external-process judgment
  boundary and deterministic policy path. It is not an evaluation of adaptive
  judgment quality.**
- These two pilots are not statistically meaningful. No comparison run has
  occurred.
- Initial selected context estimates are not total executor usage. No token
  or cost savings claim is made, and no savings percentage is calculated.
- Failures are retained as evidence. A failed first run is not retried to
  improve results.

### Reproducing

Create the ignored local configuration in each task directory from the
checked-in examples. Use absolute paths for the existing authenticated Codex
CLI JavaScript entrypoint, the current Node.js executable and
`benchmarks/tools/fixed-judgment.mjs`. Then build and run one task at a time
into a new result file:

```text
npm run build
npm run benchmark -- run benchmarks/tasks/TASK/manifest.json benchmarks/results/TASK.json --live
npm run benchmark -- report benchmarks/REPORT.md benchmarks/results/*.json
```

## Direct comparison arm (Phase 2.4g)

Implemented and fixture-tested only; **no direct run has been executed** and none is authorized by this change.

```text
npm run benchmark -- run TASK/manifest.json new-direct-result.json --live --mode direct --pair-with benchmarks/results/TASK.json
```

- Refused unless every token is present in exactly this order; `--live` is still required and the existing 3-argument
  TaskStance form is unchanged.
- The paired record must be a schema-v2 TaskStance record. Benchmark ID, upstream, baseline, manifest SHA-256 (task,
  verification, scope), source kind, executor adapter/reference, canonical executor-config SHA-256, verification and scope
  evidence, and a model present in the executor configuration are all checked before the output file is created, any
  network access, clone or Codex launch. Any mismatch is a refusal with no result.
- The model and reasoning effort are those observed in the paired record, not chosen by the direct side.
- Result schema version `3` (`mode: "direct"`) holds only the executor result, verification, changed paths, scope, change
  evidence and hashes, plus a `pairing` reference (paired result canonical SHA-256, manifest and executor-config hashes,
  pinned model/effort). It has no decision source, profile, judgment, initial-context or escalation fields. Schema v1 and
  v2 are unchanged and still validated as before.
- The reports add a "Paired comparison" section only when a direct record is present: side-by-side observations, TaskStance-only
  rows shown as `n/a` for direct, initial-context estimates labelled as estimates and never compared with executor tokens.
  No cost, savings or percentage is computed. Without direct records `REPORT.md` is generated byte-for-byte as before.

## Contracts

The authoritative schemas are in `src/benchmark/schemas.ts`. Every object is
strict, including nested task inputs, commands, executor results and comparison
configuration. Version `1` is required. `BenchmarkCatalogSchema` validates the
catalog as `{ "schema_version": "1", "tasks": [] }`.

A manifest contains:

- `benchmark_id`, canonical public GitHub `upstream_repository` HTTPS URL and
  exact 40-character lowercase `baseline_commit` SHA.
- `task`: existing TaskStance `TaskInput`, including human-readable `summary`,
  engineering classification and optional category/flags.
- `initial_context_paths`: unique declared relative files; all are mandatory.
- `taskstance_config` and `executor: { adapter: "codex", config: "..." }`;
  optional `judgment: { adapter: "process", config: "..." }`. Config references
  resolve relative to the manifest directory and must stay inside it after
  resolving symlinks. Existing adapters are used without new providers.
- `verification`: nonempty commands with unique `id`, native `executable`,
  argument-array `args`, and bounded `timeout_ms`. Shell launchers are refused.
  For npm on Windows use Node with npm's JavaScript entrypoint, not `npm.cmd`.
- `allowed_changed_paths`: anchored literal paths or patterns (`*` does not
  cross a slash; a complete `**` component matches across slashes).
- Overall CLI `timeout_ms`, plus optional public methodology `notes`.

Review manifests and configuration before adding them. Never include secrets,
private repository references, expected patches/answers, private project data,
or file hints outside declared initial context. A schema cannot determine
whether arbitrary task prose contains confidential material. Anonymous GitHub
metadata must confirm a public repository before a live clone is allowed.

## Manual live command (each live run needs separate authorization)

After separate task selection and live-run authorization (new result and report files must not already exist):

```text
npm run build
npm run benchmark -- run benchmarks/tasks/TASK/manifest.json benchmarks/results/TASK-new.json --live
npm run benchmark -- report new-report.md benchmarks/results/TASK-new.json benchmarks/results/OTHER.json
```

Output directories must exist. Output files must be new (exclusive creation).
`--live` is mandatory; there is no default task or automatic catalog execution.
The manual runner uses the existing TaskStance CLI with explicit adapter,
project/task/context/workspace arguments and optional judgment arguments.
The report command accepts only strict result records; corrupt records abort
the report rather than silently disappearing. It never filters failed records.

## Disposable workspaces and refusals

Every run creates a fresh temporary directory and an independent Git clone
(`--no-local --no-hardlinks --no-checkout`), then checks out the exact SHA in
detached HEAD state. It verifies HEAD and cleanliness before execution. Config
and input snapshots are outside the checkout. All temporary files are removed
after the run. The source checkout is never reset, cleaned, committed or pushed.
No upstream remote is edited. TaskStance itself and any of its worktrees are
refused as local sources; its upstream URL is refused in manifests.

The local-only programmatic fixture mode checks the source is clean and already
at the pinned SHA. It requires the checked-in Codex protocol double and refuses
judgment configuration or `live` mode. This is a test double behind the existing
Codex adapter, not a second executor. Normal CI runs only these local tests;
it makes zero hosted model/judgment calls or public benchmark clones.

Tracked, staged, deleted and untracked paths (including ignored files) are
collected after execution and verification and compared to allowed patterns.
HEAD, refs, Git configuration and HEAD reflog are checked for mutation.
Verification still runs after failed execution, and failures remain in results.
Dirty baselines, pin mismatches, invalid config/results, execution failures,
verification failures, metadata mutations and out-of-scope paths fail closed.
Malformed manifests are rejected before execution, without echoing their data.

The harness itself never issues Git commit/push/publish commands. Configured
verification commands and executables are trusted, reviewed programs: this is
not an OS security sandbox and cannot prevent a malicious command's side
effects. Review commands, dependencies, upstream instructions and network
requirements before authorizing live tasks. No dependency setup is implicit.

Verification commands may run executor-modified repository code, so they get a
minimal environment, not the parent's: only `PATH`, temporary-directory and
locale variables (Windows also `PATHEXT`, `SystemRoot`, `WINDIR`, `ComSpec`,
`SystemDrive`; Node/libuv on Windows always adds its fixed system/profile set
such as `USERNAME` and `USERPROFILE`). API keys, tokens, `HOME`, `NODE_OPTIONS`
and other ambient variables are not passed, and manifests cannot add any. A
verifier that needs another variable fails and is recorded as failed.

The harness's own Git commands get the same minimal environment (no parent
`GIT_*`, proxy or credential variables), never read user-level Git
configuration (`GIT_CONFIG_GLOBAL=/dev/null`; Git 2.32 or newer is required and
older Git is refused), cannot discover a repository above the checkout's parent,
and run with credential helpers and `core.fsmonitor` disabled. Machine-level
system Git configuration (for example Git for Windows' TLS and `git-lfs`
settings) remains trusted. Because repository configuration can make Git
launch helpers (such as `filter.<name>.clean`), the harness checks that the
disposable checkout's `.git` is still a real directory with unchanged `config`
and no `commondir`/`config.worktree` redirect before running any Git command
after the executor and verifiers; otherwise it records `repository_mutated`
and reports no changed paths, change evidence or scope. Live clones do not use
proxy variables.

The TaskStance CLI subprocess receives only the minimal set plus the names its
Codex adapter would forward to the executor anyway (the adapter's base set,
including home/profile directories for Codex's own sign-in files, and the
reviewed config's `inherit_env`); the adapter then applies that allowlist again.
This is environment sanitization only, not a filesystem or network sandbox: a
verifier or executor can still read files the user can read (including
credential files) and reach the network.

## Evidence and comparison fairness

Result records contain fixed failure codes, verification exit status/duration,
sorted changed paths, scope/outcome, source kind, OS/Node version, full selected
profile, decision source, observed configured judgment-call count, mandatory
retention/replan status, executor status/model/actual reasoning and optional
executor-reported input/output usage. Unobserved measurements are null/unknown.
SHA-256 hashes preserve manifest and exact config bytes without storing config
contents. Configs are validated and copied before CLI execution.

### Provenance fields added in Phase 2.4c

- `configuration.*_config_sha256` keep their meaning: SHA-256 of the exact bytes.
- `configuration.{taskstance,executor,judgment}_config_canonical_sha256`: SHA-256
  of canonical JSON (strict parse, recursively sorted object keys, array order
  preserved, no insignificant whitespace). They ignore CRLF/LF, indentation and
  key order only; values and machine-specific paths are never normalized.
  Numbers use JavaScript's JSON serialization (e.g. `1.0` and `1` are equal).
- `change_evidence`: `{ algorithm: "taskstance-change-evidence-v1", artifact_count,
  sha256 }`, computed before the disposable checkout is deleted. The hash covers,
  for every changed path in byte order, a JSON line `[path, git change state,
  kind, digest]` where kind is `file` (SHA-256 of final bytes), `symlink`
  (SHA-256 of the link target, never followed) or `deleted`. Untracked files use
  state `untracked`. No contents, prompts, output or patches are stored. Paths
  escaping the checkout, directories, or unreadable files fail the run closed
  (`harness_failed`); a passed record may not have `change_evidence: null`.

### Result schema versions

- **`schema_version: "2"`** is emitted for every newly generated result. The keys
  `configuration.{taskstance,executor,judgment}_config_canonical_sha256` and
  `change_evidence` are structurally required. They may be `null` only on failed
  runs that stopped before the evidence existed. A passed v2 result must have
  non-null raw and canonical taskstance/executor hashes, non-null raw and canonical
  judgment hashes when a judgment config is configured (otherwise the judgment
  hashes stay `null`), and non-null `change_evidence` whose `artifact_count`
  equals `changed_paths.length`. Validation rejects a v2 pass missing any of these.
- **`schema_version: "1"`** is legacy (Phase 2.4b: Pilot A/B). It remains valid
  without canonical hashes or `change_evidence`, and may not carry them (no hybrid
  records). The reporter labels these `provenance=legacy`; values are never
  reconstructed. The checked-in Pilot A/B records are unchanged and were not rerun.
- Manifest and catalog schemas remain version `"1"`.

Limitation: `taskstance-change-evidence-v1` fingerprints path, Git state, artifact
kind and final content/link-target digest, but does not distinguish mode-only
changes. A benchmark that needs mode-only provenance must introduce a new
evidence algorithm rather than silently changing v1 semantics.

`--benchmark-json` is an opt-in sanitized CLI envelope. Ordinary CLI output is
unchanged. No Core authority semantics change. Before-preparation/replan errors
may yield no envelope: escalation is then unknown, not falsely reported absent.
Judgment invocation counts include failed attempts but cannot observe provider
internal retries. Initial estimates use the existing UTF-8 byte estimator on
the actual checkout; Git line-ending settings may affect those estimates.

Duration uses a monotonic clock from harness entry through setup, execution,
verification and cleanup. Each verification also has its own duration.
Executor usage is distinct from selected **initial** context estimates. No
token-savings percentage or cost claim is inferred from context reduction.

The result schema permits `mode: "comparison"` with the same provenance and
executor/model/reasoning/config evidence. The opt-in direct arm is implemented,
but no comparison has been run; no second reviewer is implemented. Compare baseline, manifest/config
hashes, executor version, environment, task/input/verification settings and
observed model/reasoning before treating future results as comparable. Versions
of external tools are not automatically pinned or recorded by this harness.

Raw model/provider events, prompts, source contents and stderr are never written
to result/report files. Verification stdout is drained without capture. CLI JSON
and Git metadata are bounded transient inputs, validated before projection.
Local fixture evidence is not real-model performance evidence.

## Validation

The normal `npm test` suite creates only local fixture repositories and builds
the existing CLI. It covers strict schemas, dirty/ignored baselines, pin checks,
TaskStance refusal, live opt-in, local executor restrictions, scope enforcement,
verification/executor failures, malformed result leakage, metadata mutation,
source preservation, disposable cleanup and deterministic reports that retain
failures. Existing CI already runs typecheck, tests, build, pack dry-run and
the configured audit; no network benchmark step is added.
